USER / PERSON DATA MODEL
DOCUMENTAÇÃO DETALHADA DO FLUXO DE INSERTS
==========================================

1. OBJETIVO
===========

Este documento descreve a ordem correta de persistência das tabelas do módulo de cadastro de usuário/pessoa.

Ele documenta:

- finalidade de cada tabela;
- dependências entre tabelas;
- chaves estrangeiras;
- ordem do primeiro ao último INSERT;
- tabelas 1:N e N:N;
- fluxo do cadastro completo em etapas;
- ordem de seed/fake data nas migrations;
- ordem inversa para Down()/remoção;
- pontos de autenticação, autorização e auditoria.

Padrão de nomenclatura:

TABELAS = UPPER_SNAKE_CASE
CAMPOS  = UPPER_SNAKE_CASE


2. ORDEM GLOBAL DE INSERT
=========================

Ordem recomendada respeitando as Foreign Keys:

01. ORGANIZATION
02. USER_GROUP
03. CONTACT_TYPE
04. RESOURCE
05. PERMISSION
06. ROLE
07. ROLE_PERMISSION
08. PERSON
09. PERSON_DOCUMENT
10. PERSON_CONTACT
11. ADDRESS
12. USER_ACCOUNT
13. USER_ROLE
14. USER_PREFERENCE
15. REFRESH_TOKEN
16. USER_TOKEN
17. LOGIN_ATTEMPT
18. AUDIT_LOG

Nem todo cadastro de usuário insere em todas essas tabelas.

No cadastro inicial, normalmente o fluxo transacional termina em:

PERSON
PERSON_DOCUMENT
PERSON_CONTACT
ADDRESS
USER_ACCOUNT
USER_ROLE
USER_PREFERENCE
AUDIT_LOG

REFRESH_TOKEN, USER_TOKEN e LOGIN_ATTEMPT são preenchidas conforme o uso do sistema.


3. ORGANIZATION
===============

Finalidade:
Representa empresa, cliente, tenant, instituição ou organização principal.

Campos principais:

ID
    PK.

CODE
    Código único da organização.

LEGAL_NAME
    Razão social.

TRADE_NAME
    Nome fantasia.

TAX_ID
    Identificação fiscal.

EMAIL
    E-mail principal.

PHONE
    Telefone principal.

WEBSITE
    Site.

TIME_ZONE
    Fuso horário padrão.

LOCALE
    Idioma/localidade padrão.

STATUS
    Estado do registro.

CREATED_AT
UPDATED_AT
DELETED_AT

Dependências:
Nenhuma.

É criada antes de:
USER_GROUP
ROLE


4. USER_GROUP

Exemplos:
ADMINISTRATION

ID
    PK.

ORGANIZATION_ID
    FK -> ORGANIZATION.ID

CODE
NAME
DESCRIPTION
STATUS
CREATED_AT

DELETED_AT

Dependência:
ORGANIZATION

    -> ORGANIZATION_ID

INSERT USER_GROUP
    ORGANIZATION_ID = ORGANIZATION_ID

12. PERSON_CONTACT
==================

Finalidade:
Armazena quantidade ilimitada de contatos por pessoa.

Relacionamentos:

Campos:

ID

CONTACT_TYPE_ID
CONTACT_VALUE
LABEL

IS_VERIFIED
VERIFIED_AT
STATUS
CREATED_AT
UPDATED_AT
DELETED_AT

PERSON_ID:
FK -> PERSON.ID

CONTACT_TYPE_ID:
FK -> CONTACT_TYPE.ID

CONTACT_VALUE:
Valor efetivo.

Exemplos:

EMAIL:
usuario@email.com

MOBILE:
+55 51 99999-1111

WHATSAPP:
+55 51 99999-1111

PHONE:
+55 51 3333-4444

LABEL:

PERSONAL
WORK
HOME
EMERGENCY

2 e-mails
3 celulares
2 WhatsApp
1 telefone residencial
1 telefone comercial

Fluxo:

1. CONTACT_TYPE deve existir.

================

Finalidade:
Armazena credenciais, autenticação e segurança.

acesso ao sistema.

Campos:

ID

PERSON_ID:

GROUP_ID:

único.

17. REFRESH_TOKEN
=================

Finalidade:
Renovação segura da sessão/JWT.

Campos:

ID
USER_ID
TOKEN_HASH
EXPIRES_AT
CREATED_AT
REVOKED_AT
REPLACED_BY_TOKEN_ID
CREATED_BY_IP
REVOKED_BY_IP
USER_AGENT

USER_ID:
FK -> USER_ACCOUNT.ID

Não deve ser criado obrigatoriamente durante o cadastro.

Fluxo normal:

LOGIN válido
    -> gerar refresh token
    -> armazenar hash
    -> INSERT REFRESH_TOKEN

Nunca persistir token puro.


18. USER_TOKEN
==============

Finalidade:
Tokens temporários.

Usos:

PASSWORD_RESET
EMAIL_VERIFICATION
PHONE_VERIFICATION
ACCOUNT_ACTIVATION

Campos:

ID
USER_ID
TOKEN_TYPE
TOKEN_HASH
EXPIRES_AT
USED_AT
REQUESTED_BY_IP
CREATED_AT

USER_ID:
FK -> USER_ACCOUNT.ID

Exemplo:

usuário solicita recuperação de senha

    -> localizar USER_ACCOUNT
    -> gerar token
    -> calcular hash
    -> INSERT USER_TOKEN
    -> enviar token original ao usuário

21. CADASTRO COMPLETO EM ETAPAS
==============================

ETAPA 1 - PERSONAL DATA
-----------------------

Criar:

PERSON

Resultado:

PERSON_ID


ETAPA 2 - DOCUMENTS
-------------------

Para cada documento:

INSERT PERSON_DOCUMENT

FK:

PERSON_ID


ETAPA 3 - CONTACTS
------------------

Para cada contato:

1. localizar CONTACT_TYPE
2. INSERT PERSON_CONTACT

FKs:

PERSON_ID
CONTACT_TYPE_ID


ETAPA 4 - ADDRESSES
-------------------

Para cada endereço:

INSERT ADDRESS

FK:

PERSON_ID


ETAPA 5 - ACCOUNT
-----------------

Criar:

USER_ACCOUNT

FKs:

PERSON_ID
GROUP_ID

Resultado:

USER_ACCOUNT_ID


ETAPA 6 - ROLES
---------------

Para cada role selecionada:

INSERT USER_ROLE

FKs:

USER_ACCOUNT_ID
ROLE_ID


ETAPA 7 - PREFERENCES
---------------------

Criar:

USER_PREFERENCE

FK:

USER_ACCOUNT_ID


ETAPA 8 - REVIEW & FINISH
-------------------------

Validar todos os dados.

Se válidos:

INSERT AUDIT_LOG
    ACTION = REGISTRATION_COMPLETED

Retornar:

PERSON_ID
USER_ACCOUNT_ID

28. REGRAS IMPORTANTES
======================

1. PERSON não deve armazenar senha.

2. USER_ACCOUNT não deve substituir PERSON.

3. Nunca persistir senha em texto puro.

4. Nunca persistir refresh token puro.

5. PERSON_CONTACT deve permitir N contatos por pessoa.

6. CONTACT_TYPE é obrigatório para identificar o canal.

7. PERSON deve existir antes de PERSON_DOCUMENT, PERSON_CONTACT e ADDRESS.

8. PERSON deve existir antes de USER_ACCOUNT.

9. USER_ACCOUNT deve existir antes de USER_ROLE e USER_PREFERENCE.

10. RESOURCE deve existir antes de PERMISSION.

11. ROLE e PERMISSION devem existir antes de ROLE_PERMISSION.

12. O término do cadastro deve gerar AUDIT_LOG.

13. Seeds devem seguir a ordem das Foreign Keys.

14. Down() deve remover na ordem inversa.

15. O cadastro completo deve preferencialmente ser transacional.

16. IDs de seeds em migrations devem ser determinísticos para facilitar Up() e Down().

17. E-mail, telefone e WhatsApp não devem ser colunas repetidas dentro de PERSON.

18. Novos meios de contato devem ser adicionados em CONTACT_TYPE, sem alterar a estrutura de PERSON.
